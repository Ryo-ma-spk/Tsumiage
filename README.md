# tsumiage

合格までの道のりを可視化して、忘れる前に復習させ、間に合うペースに導くツール。

漠然とした不安を、名前のついた作業に変えることを目的にしている。
やらなくていい範囲を切り落とし、次にやる1つだけを提示する。

図つきのコンセプト資料は [`docs/concept.html`](docs/concept.html)。

## 考え方

**参考書でも問題集でもない。** 問題文と答えは持たない。
学ぶのは教科書・問題集の側で、このアプリは学校で学ぶことを観点として一覧にして、
次にどれを触るか指し示し、忘れる前に戻すところだけをやる。

4つの前提でできている。

1. **一回の申告で到達度を動かさない。** 問題を持たない以上、入力は申告になる。
   だから単発では信用せず、間隔をあけて複数回続いたときにだけ動かす。
   読んだだけで「できた」と振った観点は、間隔が空いた2回目で落ちる。
   チェックボックスを置かないのは、それが一回で確定してしまうから。
2. **観点には依存関係がある。** 平方根を飛ばして三平方の定理はできない。
   この依存関係（`prereqIds`）をそのままマップの形として見せる。
   ただし一本道ではない。実データは、ほぼ独立した4本の流れと4本の橋でできている。
3. **やることを選ばせない。** 何をやるか決める作業自体が受験勉強の非効率の一部なので、
   「今日」タブは次の1つだけを出す。
4. **忘れてもコマは戻さない。** 受験勉強はすごろくなので、進んだ距離（踏破）は減らさない。
   忘却で下がるのは鮮度だけにする。

単元よりも細かい「知識として定着すべき観点」を単位にしていて、
1観点 = その場で答えられるか1回で判定できる粒度に保っている。

防ごうとしている失敗が1つある。**苦手なBばかり練習した結果、得意だったはずのAを
本番で思い出せない**という反転。人は「大丈夫だと思っているもの」を復習から外すので、
放置された強みのほうが先に落ちる。何をやるかを人が決めているかぎり構造的に避けられない。

## 画面

このアプリの性格は **「自分が覚えたことが、可視化できること」**。
テストする道具でも管理する道具でもない鏡なので、**欠けても歪んでもいけない**。
判定の基準は [`docs/success-criteria.md`](docs/success-criteria.md) の7つ。

| タブ | ファイル | 役割 |
| --- | --- | --- |
| 今日 | `src/screens/TodayScreen.tsx` | 積んだ数、次の1つ、今日ぶんの残り |
| マップ | `src/screens/MapScreen.tsx` | 単元ごとの図鑑。近い順に並べ、手つかずは最後に |
| じぶん | `src/screens/StatsScreen.tsx` | 全体の帯、勘違いかも、そろそろ薄れそう |

**見出しに全体の分母を置かない。** 同じ 3/55 が上位層には燃料になり、
下位層には壁になる。分母はいつも「いま埋めている単元」にする。
全体（55個）は「じぶん」で見られる ── 閉じないが、頭には置かない。

判定の入力は `src/components/SwipeSession.tsx`。カードに出るのは観点の問いかけ
（「〜できる？」）と前回からの日数だけで、問題文も答えも出ない。それを見て
その場で思い出せたかを左右にスワイプする。上に振ると「完璧」。
誤って振ったらセッション中は1つ戻せる。

一覧にチェックボックスを並べる形は採らない。
スマホ縦持ち前提のレイアウトで、ボトムタブは3つ以上に増やさない。

### 今日ぶん

終わりの来ない画面は、どれだけ進んでも安心には変わらない。
そこで1日の目標を観点数で持ち、踏み終えたら今日タブを完了状態にする。

- 目標 = `必要ペース`（切り上げ）を 5〜10 に収めた数。下限が1セッションぶん
- 目標はその日の始まりの状態で決めて、日中は動かさない
  （途中で復習が切れて目標が伸びると、終わったはずの今日ぶんが未達に戻るため）
- 1日の区切りは 0:00 ではなく **4:00**。深夜の勉強が日付で分断されないように
- 達成の数え方は正誤を問わない。間違えた日も「やった」に数える

## 到達度の判定（`src/logic/mastery.ts`）

| 状態 | 条件 |
| --- | --- |
| 未着手 | 判定の履歴なし |
| あやしい | 振ったが「できた」が無い、または直近が「あやしい」 |
| できた | 「できた」あり。ただし定着条件に未達 |
| 定着 | 連続で2回以上できた かつ 直前から3日以上あいている |

日数はすべて暦日で数える。経過ミリ秒だと、夜に解いた人と朝に解いた人で
「3日あけた」の判定が割れてしまう。

### 踏破と鮮度は別の軸

- **踏破**（`everMastered`）— 一度でも定着に到達したか。**後戻りしない**
- **鮮度**（`freshness` 0〜1）— いま覚えている見込み。放っておけば下がる

進捗の数字は踏破で数えるので、忘れても減らない。減るのはコンディションのほう。

保持日数は観点ごとに見込む。**直前の正答からの間隔 × 2.2 × 0.6^(忘れた回数) × 反応の係数**、
4〜120日に収める。10日あけて解けたなら次は22日は持つ、という読み。
鮮度が 0 になる前に優先度が上がるので、「忘れる前に」拾える。

### 反応の係数

観点を見てから判定を振るまでの時間を測って、保持日数を微調整する。

| 時間 | 係数 | 読み |
| --- | --- | --- |
| 1.5秒未満 | × 1.0 | 想起していない疑い。伸ばさない |
| 1.5〜8秒 | × 1.2 | 即座に出た |
| 8〜25秒 | × 1.0 | 考えて出た |
| 25秒超 | × 0.9 | 難産 |
| 120秒超・欠損 | × 1.0 | 中断とみなす／古い履歴 |

**速いほど良いという単調な関係にはしていない。** 問題文を見て解く形式なら
速さは自信の表れになるが、観点名だけを見て頭の中で答えを作る形式では、
まじめにやれば数秒はかかる。1秒未満のスワイプは想起の証拠にならない。

画面には出さない。速さを褒めると当てずっぽうのスワイプが増えて、予測が壊れる。

### 「完璧」（上スワイプ）

保持日数が **× 1.5** になる。**それだけで、忘却の対象からは外れない。**

外せるようにすると「Aは完璧だから復習しない → 本番でAを忘れている」という、
このアプリが検知しようとしている失敗そのものを、利用者の手で確定させる
スイッチになる。しかも押したがるのは押すべきでない人で、主観的な確信は
勉強した直後にいちばん高くなり、実際の保持がいちばん脆いのもそのタイミング。

ここから一本、線が引ける。

> **項目を列から消す信号は入れない。間隔を動かすだけの信号なら入れてよい。**
> 後者は判定が甘くても、遅れて戻ってきて実際の結果で上書きされる。自己修正する。

先行観点がすべて「解けた」以上になると、その観点が開放される（`locked`）。
道の順序と深さは `src/logic/graph.ts` が `prereqIds` から導出する。

## ペース（`src/logic/pace.ts`）

目標は「常に全部を覚えている」ことではなく、**受験日に鮮度のピークを合わせる**こと。

- **踏破率** = 一度でも定着させた重み ÷ 出題範囲の重み（減らない）
- **コンディション** = Σ(鮮度 × 重み) ÷ 踏破した重み
- **必要ペース** = (未踏破 + 受験日までに薄れる重み) ÷ 受験日までの日数
- **実績ペース** = 直近14日で新たに踏破 + 鮮度を戻した重み ÷ 経過日数（最低3日で均す）
- **本番予測** = (受験日まで持つ重み + min(需要, 実績ペース × 残り日数)) ÷ 出題範囲の重み

実績ペースを最低3日で均すのは、始めた日に5観点やっただけで「1日5観点のペース」と
読んでしまい、着地予測が 100% に張り付くのを避けるため。1日はまだペースではない。

ペースが足りないときは「足りない」ではなく **「1日あと N つ増やせば間に合います」**
と差分で出す（`dailyShortfall()`）。診断だけ渡しても、不安が増えるだけで動けない。

重みは観点の頻出度（1〜3）で、志望校のコースごとの `emphasis` で上書きできる。
`emphasis` を 0 にするとその観点は出題範囲外として、母数からも道からも消える。

`examRiskPoints()` が「一度は解けたのに本番までに薄れる観点」を返す。
得意なつもりの観点ほど復習から漏れるので、これを名前で出すのが目的。

### セッションの構成比

1セッション5枚を **復習3 : 新規2** で固定する（`buildQueue()`）。

優先度順にそのまま5枚とると、しばらく空けたあとは復習だけで埋まって道が一歩も進まない。
テキストを頭から読み直して縄文時代ばかり詳しくなるのと同じ形になる。
何日空けても必ず新しい観点を踏むように、枠のほうを先に決めている。

片方の列が枯れたらもう片方で埋める。優先度の判断自体は `prioritize()` のままで、
`buildQueue()` がやるのは枠の配分だけ。

## データ

`src/data/curriculum.ts` に観点マスタ（**中学数学 55観点**）と志望校マスタがある。

> 領域構成と単元の並びは中学校学習指導要領（数学）に沿わせているが、
> **個々の観点への割り方・頻出度・学校名はすべて開発用の作り物**で、
> 実在の入試情報ではない。

中学数学を選んだのは範囲が狭いからではなく、**依存関係がいちばん深く取れるから**。
依存の深さは最大10、学年をまたぐ辺が20本ある。とくに
**三平方の定理（図形）が平方根（数と式）を必要とする**一本は、参考書の目次では
章が違うので見えない。マップが目次の焼き直しか本当の依存関係かは、ここで決まる。

観点体系の一次ソースは学習指導要領を想定している。公開されていて全国共通で、
出典を示せる。しかも「〜できるようにする」という能力の記述なので、
カードの `ask` にほぼそのまま変換できる。

頻出度は過去問への観点タグ付けから作る想定。観点体系そのものは全国共通にして、
志望校ごとの差は重み（0〜3）だけで持つと、マッピングの作成コストが桁で下がる。

学習状態は localStorage（キー `tsumiage.v1`）に保存される。バックエンドはまだ無い。
`useStudyStore` の `seedDemo` で動作確認用の90日分の履歴を投入できる
（進捗ゼロの画面ではボタンが出る）。

## 開発

```bash
npm install
npm run dev     # http://localhost:5173
npm run build
npm run lint
npm test        # vitest run
```

環境変数は不要。

判定条件を変えるときは、先に `src/logic/*.test.ts` を直してから実装する。
テストが仕様書を兼ねている。

## 現状の位置づけ

UIとロジックのプロトタイプ。触って方向性を確かめるためのもので、
以下はまだ手を付けていない。

- 数学1科目しかない。国語は依存関係がほぼ言えないので、
  前提2がどこで成立しなくなるかを見るのに使える
- 志望校データが本物ではない
- 認証・サーバー同期が無い（localStorage のみ）
- 保持日数の係数（間隔 × 2.2、忘却で × 0.6、反応時間で ×0.9〜1.2）は仮置き。
  実データで調整する前提
- ペースが足りないときに出題範囲を削る提案は入れていない
- 他の受験生との「ぼんやりしたランク」は検討中（`docs/concept.html` に記録）
