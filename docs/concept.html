Tsumiage

合格までの道のりを可視化して、忘れる前に復習させ、間に合うペースに導くツール。
漠然とした不安を、名前のついた作業に変えることを目的にしている。

プロトタイプ React + TypeScript + Vite 2026-08

解こうとしている問題

受験生が持っていないのは勉強時間ではなく、「いまどこにいて、あと何をやれば間に合うのか」の見取り図である。参考書は進捗を教えてくれず、模試は年に数回しか座標をくれない。その空白を埋めるために、多くの受験生は「何をやるか決める」作業に毎日の時間を使っている。

Tsumiage はこの決定を肩代わりする。到達度を判定の履歴から計算し、志望校で出ない範囲を母数から外し、残った道のりを受験日までの日数で割って、今日やる1つを出す。

参考書でも問題集でもない。問題文も答えも持たない。学ぶのは教科書や問題集の側で、このツールがやるのは、高校で学ぶことを観点として一覧にして、次にどれを触るか指し示し、忘れる前に戻すところだけである。教材を作らないぶん、観点の体系と、そこを歩く順序の設計に賭けている。

ねらいは進捗管理そのものではなく、不安を自信に変えることにある。受験生の不安は「何を忘れているか分からない」という形をしていて、対象が分からないから作業に落ちない。忘れかけている観点を名前で挙げられれば、それは不安ではなく today のリストになる。

もうひとつ、このツールが防ごうとしている失敗がある。苦手なBばかり練習した結果、得意だったはずのAを本番で思い出せないという反転である。人は「大丈夫だと思っているもの」を復習の対象から外すので、放置された強みのほうが先に落ちる。何をやるかを人が決めているかぎり、この反転は構造的に避けられない。

崩してはいけない前提

次の3つはプロダクトの主張そのもので、実装上の都合で崩さない。どれか1つを外すと、残りの2つが意味を失う構造になっている。4つ目の「踏破と鮮度を混ぜない」は、後の到達度モデルで扱う。

前提 1

一回の申告で到達度を動かさない

チェックボックスは「やった」ではなく「やった気」を記録してしまう。進捗が実力と乖離した瞬間、ダッシュボードは安心を売るだけの装置になる。

とはいえ、このツールは問題を持たない。答えを採点する主体がいない以上、入力は必然的に申告である。「自己申告を受け取らない」と言い切ることはできない。できるのは、申告を1回では信じないことのほうだ。

定着とみなす条件を「間隔をあけて2回続けてできた」に置いてある。読んだだけで「できた」を振った観点は、間隔が空いた2回目で落ちる。アプリが想起を検証できなくても、時間が検証してくれる。

到達度という状態はどこにも保存されておらず、判定履歴（Attempt）からの計算結果としてのみ存在する。チェックボックスを置かないのは、それが1回で確定してしまうからである。

守られている場所
logic/mastery.ts — evaluate() / buildStatuses()
types.ts — StudyState は target と attempts しか持たない

前提 2

観点の依存関係を UI の構造として使う

平方根を飛ばして三平方の定理はできない。この当たり前の順序は、参考書では目次の並びとして暗黙に埋まっているだけで、「いまの自分が手を出せる範囲」としては見えない。

Tsumiage は依存関係（prereqIds）を2つの用途に同時に使う。開放条件——先行観点がすべて「解けた」以上になるまでロックする——と、マップの並び順である。残りの道の長さがそのまま残量になる。

守られている場所
logic/graph.ts — トポロジカル順・深さ・子孫数
logic/mastery.ts — isUnlocked()（開放条件）
screens/MapScreen.tsx — 順序は buildStatuses の結果をそのまま使う
マップを自由配置・カンバン・カテゴリ一覧に置き換えない

前提 3

ユーザーに「何をやるか」を選ばせない

何をやるか決める作業そのものが受験勉強の非効率の一部である。選択肢を並べた時点で、アプリは決定コストを利用者に戻してしまう。

優先度の判断は prioritize() 1箇所に集約し、画面側には選定ロジックを書かない。「今日」タブが出すのは次の1観点と、本番予測の信号だけ。並び順は次の規則で固定されている。

順対象理由
1薄れている一度積み上げたものを落とすのが一番もったいない
2あやしい一度つまずいた場所は放置すると固定化する
3解けたあと1回で定着に届く
4もうすぐ薄れる7日以内に切れる見込み。忘れる前に触る
5未着手道の手前から順に

復習系は薄れるのが近い順。新しく進むぶんは、依存の浅い順 → 先に伸びる道が長い順 → 頻出度の順。ロックされた観点は候補から除外される。

最後の並びが、テキストを再開するたび頭から読み直して縄文時代ばかり詳しくなる、あの失敗を防いでいる。アプリは常に続きから出す。先頭に戻る動線がそもそも無い。

守られている場所
logic/pace.ts — prioritize() / pickNext() / buildQueue()
screens/ 配下に選定ロジックを置かない

到達度モデル

到達度は4段階で、そのうち「定着」だけが時間経過で薄れる。「いま見なくていい」は主張ではなく、この計算の結果として出てくる。

ここで2つの軸を分けていることが、このモデルのほぼすべてである。踏破は一度でも定着に到達したかどうかで、後戻りしない。鮮度はいま覚えている見込みで、放っておけば下がる。受験勉強はすごろくなので、忘れたからといってコマまで戻すことはしない。戻すのは鮮度だけにする。

状態条件
未着手判定の履歴なし
あやしい挑戦したが正答なし、または直近が誤答
解けた正答あり。ただし定着条件に未達
定着連続正答が2回以上 かつ 直前の正答から3日以上あいている
薄れている定着後、予測した保持日数を過ぎた

保持日数をどう見込むか

全観点いっせいに何日、という固定値では、得意なAと苦手なBが同じ速さで薄れることになってしまう。実際に保持できた間隔を土台にして、観点ごとに別々に見込む。

  • 保持日数の見込み 直前の正答からの間隔 × 2.2 × 0.6 忘れた回数 × 反応の係数（4〜120日に収める） 10日あけて解けたなら次は22日は持つと見込む。過去に落としている観点は割り引いて、早く戻す。
  • 鮮度 (薄れる予測日 − 今日) ÷ 保持日数　（0〜1） 0 になると復習の対象。0 になる前に拾うのが「忘れる前に復習させる」の実装。

日数はすべて暦日で数える。経過ミリ秒で数えると、夜に解いた人と朝に解いた人で「3日あけた」の判定が割れてしまう。

反応の係数

観点が出てから判定を振るまでの時間を測って、保持日数を微調整する。1.5〜8秒なら ×1.2、8〜25秒なら ×1.0、25秒超なら ×0.9。1.5秒未満と120秒超は補正しない。

ここで注意が要る。速いほど良い、という単調な関係にはしていない。問題文を見て解く形式なら速さは自信の表れになるが、観点の問いかけだけを見て頭の中で答えを作る形式では、まじめにやれば数秒はかかる。1秒未満のスワイプは思い出せた証拠ではなく、思い出そうとしていない証拠である。だから伸ばさない。

この数字は画面に出さない。速さを褒めれば当てずっぽうのスワイプが増えて、予測のほうが壊れる。問題文を持たないぶんこの信号は弱いので、係数の幅も狭めにとってある。

ペースの計算

重みは観点の頻出度（1〜3）で、志望校のコースごとの emphasis で上書きできる。 0 にするとその観点は出題範囲外として、母数からも道からも消える。これが「やらなくていい範囲を切り落とす」の実装。

目標は「常に全部を覚えている」ことではない。それは不可能だし、目指す必要もない。受験日に鮮度のピークを合わせるのが目標で、ペースの式はすべてそこから逆算されている。

  • 踏破率 一度でも定着させた重み ÷ 出題範囲の重み すごろくで進んだマス。忘れても減らない。「じぶん」のリングの外側。
  • コンディション Σ(鮮度 × 重み) ÷ 踏破した重み 踏破したうち、いま覚えている割合。上下するのはこちらの軸。
  • 必要ペース (未踏破の重み + 受験日までに薄れる重み) ÷ 受験日までの日数 復習して戻ってくるぶんを需要に数える。新規だけで割ると、いつまでも間に合う計算になってしまう。
  • 実績ペース 直近14日で新たに踏破した重み + 鮮度を戻した重み ÷ 経過日数（最低3日で均す） 復習も仕事として数える。そうしないと、復習に徹した週のペースが 0 に見える。最低3日で均すのは、始めた日に5観点やっただけで「1日5観点のペース」と読んで予測が 100% に張り付くのを避けるため。1日はまだペースではない。
  • 本番予測 (受験日まで持つ重み + min(需要, 実績ペース × 残り日数)) ÷ 出題範囲の重み 「今日」タブに出す唯一の数字。到達率ではなく、受験日に覚えている見込みの割合。

この定義にすると、冒頭のAとBの反転が自動的に拾われる。Aを放置すれば「受験日までに薄れる重み」が増えて需要が膨らみ、本番予測が下がる。そしてAは、薄れる7日前になった時点で優先度の上位に上がってくる。ユーザーがAを思い出さなくても、順番のほうがAを連れてくる。

足りないときに何を言うか

このツールの目的は不安を自信に変えることなので、「このままだと足りない」とだけ言うのは目的に反する。診断を渡されても動けないし、動けない診断は不安を増やすだけである。

そこで必要ペースと実績ペースの差を取って、「1日あと N つ 増やせば間に合います」と差分で出す。足りていれば何も出さない。

増やしても届かない場合に「範囲を削る」提案をするかは、いったん保留にしてある。実体は「頻出度1の観点を出題範囲から外す」で、出題範囲を決める経路が emphasis と2つになる。しかも一度削ると、削ったことを忘れたまま受験日を迎えるおそれがある。解除の導線と現状表示をセットで設計してからでないと入れられない。

セッションの構成比

1セッション5枚を復習3 : 新規2で固定する。優先度順にそのまま5枚とると、しばらく空けたあとは復習だけで埋まって、道が一歩も進まない。

これは、日本史を頭から読み直しては挫折し、再開するたびにまた縄文時代から始めて、縄文時代にだけ詳しくなる現象と同じ形をしている。プログラミングを始めては一生 hello world を書き直すのも同じである。戻ることそのものが悪いのではなく、戻る量を自分で決めさせるのが悪い。枠のほうを先に決めておけば、何日空けても必ず新しい土地を踏む。

片方の列が枯れたらもう片方で埋める。優先度の判断自体は変えていない。配分だけを別に持っている。

3つの画面

使うのは高校生で、触る場所は通学中のスマホである。PC の広い画面に向かって腰を据えて計画を立てる道具ではない。前提3が「決めさせない」である以上、画面は片手・縦持ち・数十秒で完結する形に寄せる。学習管理ツールの見た目ではなく、彼らが毎日開いているアプリ（Duolingo / TikTok 型）の作法を借りる。

ボトムタブは3つから増やさない。分析的な指標を「今日」に置かないことが、前提3を画面構成として守る形になる。

タブ出すもの出さないもの
今日 次の1観点、今日ぶんの残り、本番予測の信号 選択肢、分析指標
マップ 依存関係にそった道と、踏破した長さ 自由配置、カテゴリ一覧
じぶん 踏破率とコンディション、ペース、本番までに薄れる観点、いま見なくていい観点 次にやることの提案

判定の入力はスワイプカード。カードに出るのは観点の問いかけ（「〜できる？」）と前回からの日数だけで、問題文も答えも出ない。それを見てその場で思い出せたかを左右に振る。一覧にチェックボックスを並べる形は、体験として「やった気」に戻るため採らない。誤って振ったときのために、セッション中は1つ戻せる。

今日ぶん

終わりの来ない画面は、どれだけ進んでも安心には変わらない。5問やって戻ってきて、また「つぎはこれ」が出るなら、それは進捗ではなく賽の河原である。すごろくの比喩でいえば、セーブポイントがない。

そこで1日の目標を観点数で持ち、踏み終えたら今日タブを完了状態にする。目標は必要ペースから出して 5〜10 に収める。下限を1セッションぶんにそろえてあるので、「はじめる → 終わった」が一往復で完結する。

細部が2つある。目標はその日の始まりの状態で決めて、日中は動かさない。途中で復習が切れて目標が伸びると、終わったはずの今日ぶんが未達に戻ってしまうからである。そして1日の区切りは 0:00 ではなく 4:00 に置く。深夜に勉強して日付をまたぐ層が対象なので、23:50 に始めたセッションが分断されるのは理不尽でしかない。

達成の数え方は正誤を問わない。間違えた日も「やった」に数える。前提4と同じ考えで、頑張りのほうは取り消さない。

データ設計の要

観点は単元より細かい「知識として定着すべき1つの粒度」で、1観点 = その場で答えられるか1回で判定できるところまで割る。ここが製品の本体であり、最大のコストでもある。

観点体系の一次ソースは学習指導要領を想定している。公開されていて、全国共通で、出典を示せる。しかも「〜できるようにする」という能力の記述なので、カードの問いかけにほぼそのまま変換できる。教材を持たないという選択が、ここで体系の作りやすさに返ってくる。志望校ごとの差は重み（0〜3）だけで持つ。

設計上の賭けは、観点体系そのものを全国共通にして、志望校ごとの差を重み（0〜3）だけで持つという点にある。学校ごとに観点体系を作るとマッピングの作成コストが学校数に比例するが、この形なら「観点数 × 1回のタグ付け」＋「コース数 × 重み付け」に分解できる。頻出度は本来、過去問への観点タグ付けから作る。

検討中：ぼんやりしたランク

他の受験生のなかで自分がどのあたりにいるかを、明確な順位ではなく帯で見せる案がある。任天堂がオンラインの順位を正確な数字で出さないのと同じ理屈で、「頑張ったのに世界4000位です」と言われて嬉しい人はいない。目的が不安の解消である以上、精度より粒度のほうが大事になる。

ただし持ち込むときに条件が1つある。母集団を「このアプリの利用者」にすると、ほぼ意味を持たない。志望校も受験日もばらばらな集団のなかでの位置は、安心にも危機感にもつながらない。比較が効くのは「同じ志望校で、受験日までの残り日数が近い人」のなかでの帯だけである。

  • 前提バックエンドが要る。いまは localStorage のみで、他人のデータを1件も持っていない
  • 前提利用者が高校生なので、学習データを集めるなら未成年のデータ収集としての設計が要る。技術ではなく事業判断の側
  • 前提初期は N が足りず帯が出ない。まずは受験日から逆算した固定の基準線に対する帯から始めるほうが現実的

いまの位置

UI とロジックのプロトタイプ。触って方向性を確かめるためのもので、ビルド・lint・テストはいずれもクリーン。

  • 実装済み踏破と鮮度の分離、観点ごとの保持日数の予測、開放条件、志望校による絞り込み、受験日から逆算したペース計算、3画面とスワイプ判定
  • 実装済みマップの並びを prereqIds から導出。依存の順序と表示の順序が一致した
  • 実装済み今日ぶんの単位と完了状態、セッションの構成比、反応時間による補正、スワイプの取り消し、不足時の差分表示
  • 実装済みlogic/ のテスト75件。暦日での判定、落としたあとの再定着、踏破率の単調性、本番までに薄れる観点の抽出、ブランク後に新規が必ず入ること、今日ぶんの目標が日中に動かないことを固定した
  • 実装済み開発確認用に中学数学55観点（深さ10・学年をまたぐ辺20本）。深い依存を入れて初めて出た不具合を3つ直した — 開放数を超える今日ぶんの目標、踏破ゼロのときの赤い 0%、根っこの観点に「よく出る」としか言えないこと
  • 未着手受験する科目をそろえる（いまは数学1科目のみ）。国語は依存関係がほぼ言えないので、前提2がどこで成立しなくなるかを見るのに使える
  • 未着手志望校データの本番化（過去問への観点タグ付けによる頻出度）
  • 未着手認証とサーバー同期。永続化は localStorage のみで端末を変えると消える
  • 未検証保持日数の係数（間隔 × 2.2、忘却で × 0.6、反応時間で ×0.9〜1.2）は仮置き。実データで調整する前提の数字であって、根拠のある値ではない
  • 未実装ペースが足りないときに出題範囲を削る提案。設計してから入れる
データについての注記。観点の領域構成と単元の並びは中学校学習指導要領（数学）に沿わせていますが、個々の観点への割り方・頻出度・学校名・コースはすべて開発用の作り物です。実在の入試情報ではありません。実データを扱う際は必ず出典を伴わせます。
